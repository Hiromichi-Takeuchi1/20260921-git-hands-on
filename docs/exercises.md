# 演習用 Issue 案

一覧・詳細、検索とカテゴリの併用、該当なしの案内、画像の代替表示は実装済みです。以下は、できあがったサイトを共同で育てるための Issue 案です。Issue のタイトル・目的・完了条件をそのまま GitHub に転記できます。1 人ですべて取り組む必要はありません。

## 進め方の例（約 40 人）

参加者に `p01`〜`p40` の識別子を割り当て、まず各自が店舗を 1 件追加します。追加 PR はペアでレビューし、講師または担当者がマージします。全員が `upstream/main` を取り込み、`index.html` の「店舗データを読み込む」から最新の `src/shops/` の全 JSON を選び直したら、隣の人の店舗を改善する役、共通機能を改善する役などに分かれます。

共通ファイルを触る Issue は先に担当を決めます。大きな機能は UI、動作、検証に細分化して合意してから進めてください。レビュアーは「何が良いか」「どの利用者が困るか」「どう直すと良さそうか」を具体的に伝えます。作者は同じブランチに修正を push し、レビューをもう一度受けます。

ローカル確認は `index.html` を直接開いて行います。店舗 JSON の変更後は全 JSON を選び直し、HTML・CSS・JavaScript の変更後はブラウザを再読込してください。参加者の Node.js・npm は不要で、PR の検証とビルドは GitHub Actions が実行します。

## 初級：データや文章を改善する

### 1. 自分の架空のお店を追加する

**目的：** 共有ファイルに触れず、1 店舗分の変更を PR にまとめる。

**主な対象：** `src/shops/p01-nami-cafe.json`（自分の ID に置き換える）、任意で `images/shops/`。

**完了条件：**

- ひな形をコピーし、重複しない ID と架空の店舗情報を入力している。
- おすすめ商品・サービスが 1 件以上ある。
- 一覧・検索・カテゴリ絞り込み・詳細表示で自分の店舗を確認している。
- 画像を省略した場合も共通イラストで表示でき、ブラウザでのデータ検証と PR の CI が成功する。

### 2. 別の参加者のお店の紹介文を改善する

**目的：** 最新の変更を取り込み、他の人の成果を読みながら改善する。

**主な対象：** 担当を確認した店舗の JSON。

**完了条件：**

- 元の作者と相談し、対象を 1 店舗に絞っている。
- お店の魅力やおすすめの利用場面が分かる文章にしている。
- 価格・営業時間など、今回の目的に関係しない情報を不用意に変えていない。
- PR に変更前後の文章と、改善した理由を記載している。

### 3. 商店街のお知らせを 1 件追加する

**目的：** 共有データへの変更を小さくまとめる。

**主な対象：** `src/data/news.js`。

**完了条件：**

- 既存のデータ形式に合わせ、架空のイベントや活動を追加している。
- 日付・タイトル・本文が分かりやすく、既存のお知らせが消えていない。
- トップページで PC・スマートフォンの両方から読める。
- 外部リンクや動かない予約ボタンを追加していない。

### 4. 店舗のオリジナル SVG を作る

**目的：** 画像と店舗データの関係を理解する。

**主な対象：** 自分の店舗 JSON と `images/shops/`。

**完了条件：**

- 自作のローカル SVG を追加し、相対パスで参照している。
- `imageAlt` に画像の特徴を説明している。
- カードと詳細の両方で重要な部分が切れずに見える。
- HTML を直接開き、JSON の読み込み後に画像を確認し、PR の CI も成功している。

## 中級：共通の表示・操作を改善する

### 5. キーボード操作と読み上げを点検・改善する

**目的：** 操作しやすさを、実際の確認結果から改善する。

**主な対象：** `index.html`、`shop.html`、`src/styles.css`、必要な JavaScript。

**完了条件：**

- Tab と Enter を使い、検索・カテゴリ・詳細・一覧への戻りを一通り確認している。
- 現状で改善できる点を 1 件選び、利用者への影響を PR に説明している。
- 変更後もフォーカスが見え、ラベルと操作の順序が分かる。
- 過剰な ARIA 属性や、不要な読み上げの繰り返しを増やしていない。

### 6. 長い店名・説明でも読みやすいカードにする

**目的：** 他の参加者のデータが増えた状況で、共通 CSS の影響を理解する。

**主な対象：** `src/styles.css`。

**完了条件：**

- 手元で短い店名と長い店名を比較し、必要な余白や行間を改善している。
- 375px と PC 幅で横スクロールや文字の重なりがない。
- 店舗名やリンクなど、必要な情報を隠していない。
- 確認のためだけに作った仮データは PR に残していない。

### 7. 店舗一覧に並び替えを追加する

**目的：** 検索・カテゴリに新しい操作を組み合わせる。

**主な対象：** `index.html`、`src/main.js`、`src/styles.css`。

**完了条件：**

- 「店名：あ→わ」「店名：わ→あ」を選べるラベル付きの選択欄がある。
- 店名順は日本語を考慮した比較で並び替える。
- 検索・カテゴリ絞り込みの状態を保ったまま並び替えられる。
- 0 件・1 件の場合も正常に表示され、店舗データ自体を書き換えない。

### 8. 詳細ページに「同じカテゴリのお店」を追加する

**目的：** 共通のデータ読込処理を利用して回遊を増やす。

**主な対象：** `src/shop.js`、`src/styles.css`。

**完了条件：**

- 同じカテゴリの別のお店を最大 3 件表示する。
- 表示中の店舗自身を候補に含めない。
- 候補がないときに空の見出しや壊れたリンクを表示しない。
- ローカルでは読み込んだ店舗情報を遷移先にも引き継ぎ、公開サイトでは詳細 URL を直接開ける。
- GitHub Pages のリポジトリ配下でもリンクが動く。

## 発展：状態や品質を扱う

### 9. お気に入りをこのブラウザに保存する

**目的：** サーバーを使わず、画面の状態を保存する。

**主な対象：** `src/main.js`、`src/shop.js`、必要な共通 JavaScript と CSS。

**完了条件：**

- 店舗をお気に入りに登録・解除でき、状態が見た目と支援技術に伝わる。
- `localStorage` を使い、利用できるブラウザでは再読込しても状態が残る。HTML を直接開く場合と公開サイトの両方で確認する。
- 保存領域が使えない場合や保存内容が壊れた場合でも、店舗一覧を表示できる。
- 「このブラウザに保存される」ことが分かり、ログインや外部通信は不要である。

### 10. 検索条件を URL で共有できるようにする

**目的：** UI の状態と URL の対応を設計する。

**主な対象：** `src/main.js`。

**完了条件：**

- 検索語とカテゴリを URL のクエリから復元できる。
- 検索条件を変えるとページ再読込なしで URL に反映される。
- 日本語・空文字・未知のカテゴリでも壊れない。
- ブラウザの戻る・進むの扱いをチームで決め、PR に仕様と確認結果を書いている。
- 詳細ページ用の `id` と混同せず、リポジトリ配下のパスとローカルプレビュー用のデータを維持する。

### 11. 店舗データの検証エラーをより直しやすくする

**目的：** 既存の必須チェックを保ち、開発する人向けの表示を改善する。

**主な対象：** `src/data/shop-validation.js` とブラウザの検証表示。CLI も変更する場合は `scripts/`。

**完了条件：**

- 既存のエラー表示を読んで、改善するケースを 1 つ選んでいる。
- たとえば未知のカテゴリに、入力値と使用できる値を合わせて表示する。
- ファイル名・項目名・直し方が読み取れる。
- ブラウザで正常なデータを読み込め、一時的に壊したデータには適切なエラーが出ることを確認している。
- CLI も変更した場合は、Node.js がある環境または CI で終了コードも確認している。
- エラー確認用の壊れた店舗ファイルをコミットしていない。

### 12. 検索とカテゴリ絞り込みの組み合わせを自動確認する

**目的：** 実装の形ではなく、利用者に必要な挙動を検証する。

**主な対象：** フィルタ処理と、ブラウザで直接開けるテスト用 HTML・JavaScript。

**完了条件：**

- 店名一致、紹介文一致、カテゴリとの組み合わせ、該当なしを確認できる。
- 本番の店舗数や特定の文言に依存しない小さなテストデータを使う。
- 画面の挙動を変えず、初学者が追える範囲で検証可能にする。
- テスト用 HTML の開き方を README に記載する。
- Node.js・npm のインストールを参加者の必須手順に追加しない。

## 講師向け：2 人でコンフリクトを解消する演習

### 準備

2 人（A さん・B さん）が **同じ `upstream/main` のコミットから**始め、README の同じ 1 行を異なる文章に変更します。対象は README 冒頭の次の行です。

```text
海の近くにある、少しレトロな架空の商店街の地域ポータルです。
```

実施前に講師がこの行を確認してください。複数ペアで同時実施すると他の変更も混ざるため、全体で 1 ペアを実演するか、ペアごとに別の演習リポジトリを用意します。店舗追加と独立した PR にして、実際の文言改善として完了できるようにします。

### 1. 2 人が同じ状態を取り込む

A さん・B さんともに、未コミットの変更がないことを確認して次を実行します。

```sh
git status
git switch main
git fetch upstream
git merge --ff-only upstream/main
git push origin main
git rev-parse --short HEAD
```

最後に出るコミット ID が 2 人で同じことを確認します。この時点から、B さんが自分の変更をコミットするまでは、A さんの PR をマージしません。

### 2. A さんが同じ行を変更して PR を作る

```sh
git switch -c practice/a-town-intro
```

対象行を次のように書き換えます。

```text
海風が心地よい、少しレトロな架空の商店街の地域ポータルです。
```

```sh
git add README.md
git commit -m "商店街の紹介に海風の雰囲気を加える"
git push -u origin practice/a-town-intro
```

元リポジトリの `main` に向けて PR を作成します。

### 3. B さんも元の同じ行を変更して PR を作る

B さんはまだ A さんの変更を取り込まず、手順 1 の状態から進めます。

```sh
git switch -c practice/b-town-intro
```

対象行を次のように書き換えます。

```text
海の近くにある、小さなお店との出会いが楽しい架空の商店街の地域ポータルです。
```

```sh
git add README.md
git commit -m "商店街の紹介にお店との出会いを加える"
git push -u origin practice/b-town-intro
```

元リポジトリの `main` に向けて PR を作成します。

### 4. 講師が A さんの PR を先にマージする

B さんの PR をレビューし、GitHub 上で競合があることを一緒に確認します。Git が判断できないのは「どちらの文章を採用するか」であることを伝え、2 人の意図を聞きます。

### 5. B さんが最新の main を作業ブランチに取り込む

```sh
git switch practice/b-town-intro
git fetch upstream
git merge upstream/main
```

同じ行を変更したため、`README.md` にコンフリクトが発生して merge が停止します。

```sh
git status
git diff
```

エディタで README を開くと、次のような印が表示されます。

```text
<<<<<<< HEAD
海の近くにある、小さなお店との出会いが楽しい架空の商店街の地域ポータルです。
=======
海風が心地よい、少しレトロな架空の商店街の地域ポータルです。
>>>>>>> upstream/main
```

`HEAD` 側が B さんの作業ブランチ、`upstream/main` 側が A さんの変更を取り込んだ元リポジトリです。両方の意図を踏まえ、たとえば以下の 1 行に書き換えます。`<<<<<<<`・`=======`・`>>>>>>>` はすべて削除します。

```text
海風が心地よく、小さなお店との出会いが楽しい、少しレトロな架空の商店街の地域ポータルです。
```

### 6. 解消を確認し、同じ PR に追加 push する

```sh
git diff --check
git diff
git add README.md
git diff --cached
git commit -m "元リポジトリを取り込み、紹介文のコンフリクトを解消"
git push origin practice/b-town-intro
```

コミットの前に、競合マーカーが残っていないことと、意図した文章になっていることをエディタでも確認します。既存の B さんの PR に解消結果が反映されます。PR の **Validate and build** が成功することも確認します。force push や新しい PR は不要です。A さんが解消後の文章をレビューし、講師が B さんの PR をマージします。

解消作業をいったんやり直したい場合は、merge のコミット前に `git merge --abort` で merge 開始前に戻せます。すでに commit した後には使わず、状況を講師と確認してください。

### 7. 2 人とも取り込んで振り返る

```sh
git switch main
git fetch upstream
git merge --ff-only upstream/main
git push origin main
```

2 人で最終的な README を確認します。「同じ行を変えたため競合した」「他の人の変更の意味を確認して解消した」「別々の店舗ファイルなら通常は競合しにくい」を振り返り、次の作業を最新の `main` から始めます。
