# 演習用 Issue 案

一覧・詳細、検索とカテゴリの併用、該当なしの案内、共通イラストは実装済みです。以下は、できあがったサイトを共同で育てるための Issue 案です。Issue のタイトル・目的・完了条件をそのまま GitHub に転記できます。1 人ですべて取り組む必要はありません。

## 進め方の例（約 40 人）

参加者に `p01`〜`p40` の識別子を割り当て、各自の店舗詳細 HTML とトップページのカードを追加します。追加 PR はペアでレビューし、講師または担当者がマージします。全員が `upstream/main` を取り込み、`index.html` を再読込して、お互いのお店を見られることを確認します。次は隣の人の店舗を改善する役、共通の表示を改善する役などに分かれます。

`index.html` はみんなで編集するファイルです。店舗追加は小グループごとに進め、数件のマージごとに最新状態を取り込む時間を設けると整理しやすくなります。同じ位置へのカード追加が競合したら、両方のカードを残すよう相談して解消します。ファイル全体の整形・並び替えは店舗追加と別の PR にしてください。

共通 CSS や機能を触る Issue は先に担当を決めます。大きな機能は画面・動作・確認に分けて合意してから進めてください。レビュアーは、利用者への影響と改善案を具体的に伝えます。作者は同じブランチに修正を push し、レビューをもう一度受けます。

ローカル確認は `index.html` を直接開いて行います。HTML・CSS・JavaScript を保存したらブラウザを再読込します。参加者の Node.js・npm・Python は不要です。PR の GitHub Actions ではリンクなどを検証します。見た目と操作はブラウザでも確認してください。

## 初級：HTML と文章を改善する

### 1. 自分の架空のお店を追加する

**目的：** 1 店舗分の変更を小さな PR にまとめる。

**主な対象：** `shops/p01-nami-cafe.html`（自分のファイル名に置き換える）、`index.html`、任意で `images/shops/`。

**完了条件：**

- 詳細のひな形をコピーし、重複しないファイル名と架空の店舗情報に書き換えている。
- おすすめ商品・サービスと価格が 1 件以上ある。
- 一覧にカードを追加し、詳細と店名・カテゴリ・紹介内容を揃えている。
- 一覧・検索・カテゴリ絞り込み・詳細・一覧へ戻るリンクを確認している。
- 画像がなければひな形の共通イラストを使い、PR の CI が成功する。

### 2. 別の参加者のお店の紹介文を改善する

**目的：** 最新の変更を取り込み、他の人の成果を読みながら改善する。

**主な対象：** 担当を確認した `shops/` の HTML、必要に応じて `index.html` の該当カード。

**完了条件：**

- 元の作者と相談し、対象を 1 店舗に絞っている。
- お店の魅力やおすすめの利用場面が分かる文章にしている。
- 一覧の短い紹介と、詳細の詳しい紹介に食い違いがない。
- 価格・営業時間など、今回の目的に関係しない情報を不用意に変えていない。
- PR に変更前後の文章と、改善した理由を記載している。

### 3. 商店街のお知らせを 1 件追加する

**目的：** 共通 HTML への変更を小さくまとめる。

**主な対象：** `index.html` のお知らせ欄。

**完了条件：**

- 既存のお知らせを見本に、架空のイベントや活動を追加している。
- 日付・タイトル・本文が分かりやすく、既存のお知らせが消えていない。
- トップページで PC・スマートフォンの両方から読める。
- 動かない予約ボタンを追加していない。

### 4. 店舗のオリジナル SVG を作る

**目的：** 画像の置き場所と相対パスの関係を理解する。

**主な対象：** 自分の詳細 HTML、`index.html` の該当カード、`images/shops/`。

**完了条件：**

- 自作のローカル SVG を追加し、相対パスで参照している。
- `img` の `alt` に画像の特徴を説明している。
- 一覧からは `images/shops/…`、詳細からは `../images/shops/…` で参照している。
- カードと詳細の両方で重要な部分が切れずに見える。
- HTML を直接開いて画像を確認し、PR の CI も成功している。

## 中級：共通の表示・操作を改善する

### 5. キーボード操作と読み上げを点検・改善する

**目的：** 操作しやすさを、実際の確認結果から改善する。

**主な対象：** `index.html`、対象の `shops/*.html`、`src/styles.css`、必要な JavaScript。

**完了条件：**

- Tab と Enter を使い、検索・カテゴリ・詳細・一覧への戻りを一通り確認している。
- 現状で改善できる点を 1 件選び、利用者への影響を PR に説明している。
- 変更後もフォーカスが見え、ラベルと操作の順序が分かる。
- 過剰な ARIA 属性や、不要な読み上げの繰り返しを増やしていない。
- 詳細の共通構造を変えた場合は `templates/shop-template.html` にも反映している。

### 6. 長い店名・説明でも読みやすいカードにする

**目的：** 他の参加者の店舗が増えた状況で、共通 CSS の影響を理解する。

**主な対象：** `src/styles.css`。

**完了条件：**

- 手元で短い店名と長い店名を比較し、必要な余白や行間を改善している。
- 375px と PC 幅で横スクロールや文字の重なりがない。
- 店舗名やリンクなど、必要な情報を隠していない。
- 確認のためだけに作った仮の店舗は PR に残していない。

### 7. 店舗一覧に並び替えを追加する

**目的：** 検索・カテゴリに新しい操作を組み合わせる。

**主な対象：** `index.html`、`src/main.js`、`src/styles.css`。

**完了条件：**

- 「店名：あ→わ」「店名：わ→あ」を選べるラベル付きの選択欄がある。
- カードの店名を日本語を考慮した比較で並び替える。
- 検索・カテゴリ絞り込みの状態を保ったまま並び替えられる。
- 0 件・1 件の場合も正常に表示される。
- 店舗の内容を JavaScript に二重管理せず、既存の HTML を利用している。

### 8. 詳細ページに「近くのお店」を追加する

**目的：** ページ間のリンクを作り、お店を巡りやすくする。

**主な対象：** 担当を決めた `shops/` の HTML、必要に応じて `src/styles.css`。

**完了条件：**

- 作者と相談して、別のお店を 1〜3 件選んで紹介している。
- 店名と短い紹介、詳細ページへのリンクがある。
- 存在しない店舗や表示中の店舗自身にリンクしていない。
- HTML を直接開いた場合と、リポジトリ配下の公開 URL の両方で使える相対パスである。
- リンク先の店名を変えたときに更新する必要があることを、PR に記載している。

## 発展：状態や品質を扱う

### 9. お気に入りをこのブラウザに保存する

**目的：** サーバーを使わず、画面の状態を保存する。

**主な対象：** `index.html`、`src/main.js`、`src/styles.css`。

**完了条件：**

- 店舗をお気に入りに登録・解除でき、状態が見た目と支援技術に伝わる。
- `localStorage` を使い、利用できるブラウザでは再読込しても状態が残る。
- HTML を直接開く場合と公開サイトの両方で確認する。
- 保存領域が使えない場合や保存内容が壊れた場合でも、店舗一覧を表示できる。
- 「このブラウザに保存される」ことが分かり、ログインや外部通信は不要である。

### 10. 検索条件を URL から復元できるようにする

**目的：** 画面の状態と URL の対応を設計する。

**主な対象：** `src/main.js`。

**完了条件：**

- 検索語とカテゴリを URL のクエリまたはハッシュから復元できる。
- 日本語・空文字・未知のカテゴリでも壊れない。
- ブラウザの戻る・進むの扱いをチームで決め、PR に仕様と確認結果を書いている。
- ローカルの HTML 直接起動と、公開先のリポジトリ配下の URL を保つ。
- 共有する URL は公開サイトのものを使い、PC 固有の `file://` URL と区別して説明する。

### 11. リンク検証のエラーをより直しやすくする

**目的：** 既存のチェックを保ち、開発する人向けの表示を改善する。

**主な対象：** `scripts/check-links.py`。Python を扱える参加者向け。

**完了条件：**

- 既存のエラー表示を読んで、改善するケースを 1 つ選んでいる。
- たとえば画像が見つからないとき、HTML のある場所から相対パスを確認する案内を付ける。
- ファイル名・問題の参照先・直し方が読み取れる。
- 一時的に壊した参照先でエラーが出ることと、正常なサイトで成功することを確認している。
- エラー確認用に壊した HTML を元に戻し、コミットに含めていない。
- Python を通常の参加者の必須準備には追加していない。

### 12. 検索とカテゴリ絞り込みの組み合わせを自動確認する

**目的：** 実装の形ではなく、利用者に必要な挙動を検証する。

**主な対象：** フィルタ処理と、ブラウザで直接開けるテスト用 HTML・JavaScript。

**完了条件：**

- 店名一致、紹介文一致、カテゴリとの組み合わせ、該当なしを確認できる。
- 本番の店舗数や特定の文言に依存しない小さなカードの例を使う。
- 画面の挙動を変えず、初学者が追える範囲で検証可能にする。
- テスト用 HTML の開き方を README に記載する。
- Node.js・npm のインストールを参加者の必須手順に追加しない。

## 講師向け：2 人でコンフリクトを解消する演習

### 準備

2 人（A さん・B さん）が **同じ `upstream/main` のコミットから**始め、README の同じ 1 行を異なる文章に変更します。対象は README 冒頭の次の行です。

```text
海の近くにある、少しレトロな架空の商店街の地域ポータルです。
```

実施前に講師がこの行を確認してください。複数ペアで同時実施すると他の変更も混ざるため、全体で 1 ペアを実演するか、ペアごとに別の演習リポジトリを用意します。店舗追加と独立した PR にして、実際の文言改善として完了できるようにします。

### 1. 2 人が同じ状態を取り込む

A さん・B さんともに、未コミットの変更がないことを確認して次を実行します。

```sh
git status
git switch main
git fetch upstream
git merge --ff-only upstream/main
git push origin main
git rev-parse --short HEAD
```

最後に出るコミット ID が 2 人で同じことを確認します。この時点から、B さんが自分の変更をコミットするまでは、A さんの PR をマージしません。

### 2. A さんが同じ行を変更して PR を作る

```sh
git switch -c practice/a-town-intro
```

対象行を次のように書き換えます。

```text
海風が心地よい、少しレトロな架空の商店街の地域ポータルです。
```

```sh
git add README.md
git commit -m "商店街の紹介に海風の雰囲気を加える"
git push -u origin practice/a-town-intro
```

元リポジトリの `main` に向けて PR を作成します。

### 3. B さんも元の同じ行を変更して PR を作る

B さんはまだ A さんの変更を取り込まず、手順 1 の状態から進めます。

```sh
git switch -c practice/b-town-intro
```

対象行を次のように書き換えます。

```text
海の近くにある、小さなお店との出会いが楽しい架空の商店街の地域ポータルです。
```

```sh
git add README.md
git commit -m "商店街の紹介にお店との出会いを加える"
git push -u origin practice/b-town-intro
```

元リポジトリの `main` に向けて PR を作成します。

### 4. 講師が A さんの PR を先にマージする

B さんの PR をレビューし、GitHub 上で競合があることを一緒に確認します。Git が判断できないのは「どちらの文章を採用するか」であることを伝え、2 人の意図を聞きます。

### 5. B さんが最新の main を作業ブランチに取り込む

```sh
git switch practice/b-town-intro
git fetch upstream
git merge upstream/main
```

同じ行を変更したため、`README.md` にコンフリクトが発生して merge が停止します。

```sh
git status
git diff
```

エディタで README を開くと、次のような印が表示されます。

```text
<<<<<<< HEAD
海の近くにある、小さなお店との出会いが楽しい架空の商店街の地域ポータルです。
=======
海風が心地よい、少しレトロな架空の商店街の地域ポータルです。
>>>>>>> upstream/main
```

`HEAD` 側が B さんの作業ブランチ、`upstream/main` 側が A さんの変更を取り込んだ元リポジトリです。両方の意図を踏まえ、たとえば以下の 1 行に書き換えます。`<<<<<<<`・`=======`・`>>>>>>>` はすべて削除します。

```text
海風が心地よく、小さなお店との出会いが楽しい、少しレトロな架空の商店街の地域ポータルです。
```

### 6. 解消を確認し、同じ PR に追加 push する

```sh
git diff --check
git diff
git add README.md
git diff --cached
git commit -m "元リポジトリを取り込み、紹介文のコンフリクトを解消"
git push origin practice/b-town-intro
```

コミットの前に、競合マーカーが残っていないことと、意図した文章になっていることをエディタでも確認します。既存の B さんの PR に解消結果が反映されます。PR の **Check site** が成功することも確認します。force push や新しい PR は不要です。A さんが解消後の文章をレビューし、講師が B さんの PR をマージします。

解消作業をいったんやり直したい場合は、merge のコミット前に `git merge --abort` で merge 開始前に戻せます。すでに commit した後には使わず、状況を講師と確認してください。

### 7. 2 人とも取り込んで振り返る

```sh
git switch main
git fetch upstream
git merge --ff-only upstream/main
git push origin main
```

2 人で最終的な README を確認します。「同じ行を変えたため競合した」「他の人の変更の意味を確認して解消した」「別々の詳細ページは競合しにくくても、一覧は共有しているので変更範囲を小さくする」を振り返り、次の作業を最新の `main` から始めます。
